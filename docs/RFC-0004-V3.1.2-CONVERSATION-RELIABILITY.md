# RFC-0004 — MARTCOM AI V3.1.2
## Semantic Memory & Conflict Resolver

**Estado:** DESIGN  
**Versión objetivo:** 3.1.2  
**Módulo principal:** Semantic Engine  
**Impacto esperado:** alto  
**Riesgo de despliegue:** medio  
**Compatibilidad:** debe ser retrocompatible con V3.1.1 / V3.1.0 de memoria existente.

---

# 1. Problema

MARTCOM AI ya conserva memoria e intención, pero todavía interpreta algunas frases de forma demasiado literal.

Caso real observado:

```text
Cliente: No tengo trabajo
Cliente: Estoy desempleado
```

Ambas frases expresan exactamente el mismo estado, pero el sistema puede tratarlas como información diferente y activar:

```text
aclarar_contradiccion
```

Esto puede provocar bucles de preguntas como:

```text
¿Sigues desempleado?
¿Estás desempleado o trabajando?
¿Sigues sin trabajar?
```

También se observó que una frase conversacional como:

```text
Ya te había dicho que estoy desempleado
```

puede ser interpretada erróneamente como nombre.

Otro caso:

```text
Cliente: No tengo NSS, pero te puedo dar mi CURP
```

El sistema debe aprovechar el dato alternativo y continuar, no volver a preguntas laborales ya resueltas.

---

# 2. Objetivo

Agregar una capa semántica determinista entre Intent Engine y Memory Engine.

Nuevo flujo:

```text
Mensaje
  ↓
Intent Engine
  ↓
Semantic Normalizer
  ↓
Conflict Resolver
  ↓
Slot Resolver
  ↓
Memory Engine
  ↓
Planner
```

El Semantic Engine no redacta respuestas y no toma decisiones comerciales.

---

# 3. Alcance V3.1.2

## 3.1 Semantic Normalizer

Normalizar expresiones equivalentes.

Ejemplo laboral:

```text
"No tengo trabajo"
"Estoy desempleado"
"No estoy trabajando"
"Estoy sin empleo"
"Actualmente no laboro"
```

Resultado:

```json
{
  "tipo_trabajo": "desempleado"
}
```

Ejemplo IMSS:

```text
"No tengo IMSS"
"No estoy afiliado"
"No cuento con seguro"
"Me dieron de baja del IMSS"
```

Resultado contextual esperado:

```json
{
  "tiene_imss": false
}
```

---

## 3.2 Conflict Resolver 2.0

Una contradicción solo existe cuando los valores normalizados son incompatibles.

No contradicción:

```text
desempleado
desempleado
```

Contradicción real:

```text
desempleado
empleado
```

El motor debe distinguir además cambios temporales:

```text
Antes estaba desempleado, pero ya conseguí trabajo.
```

Esto puede ser una actualización de estado, no necesariamente un conflicto.

---

## 3.3 Resolución única

Cada conflicto tendrá un identificador estable:

```text
tipo_trabajo:desempleado|empleado
```

La memoria guardará:

```json
{
  "conflictos_resueltos": []
}
```

Si ya fue preguntado y resuelto, no podrá volver al planner como pendiente.

---

## 3.4 Name Extractor 2.0

El sistema rechazará como nombre frases conversacionales.

Palabras o estructuras de alto riesgo:

```text
estoy
tengo
quiero
necesito
trabajo
desempleado
imss
afore
curp
nss
ya te dije
ya había dicho
no tengo
```

Ejemplos válidos:

```text
Miguel Axel Yañez Casanova
María Fernanda Carranza Alvarez
César Julián Palmillas Gómez
```

Ejemplos inválidos:

```text
Ya te había dicho que estoy desempleado
No tengo NSS
Quiero información
Estoy trabajando
```

El extractor debe priorizar patrones explícitos:

```text
Me llamo ...
Mi nombre es ...
Soy [nombre], ...
```

sin interpretar cualquier frase libre como identidad.

# 4. Slot Filling

El sistema manejará datos requeridos como slots.

Ejemplo:

```json
{
  "slots": {
    "nombre": "confirmado",
    "edad": "confirmado",
    "tipo_trabajo": "confirmado",
    "tiene_imss": "confirmado",
    "curp": "pendiente",
    "nss": "no_disponible"
  }
}
```

Caso:

```text
No tengo NSS, pero te puedo dar mi CURP.
```

Resultado esperado:

```json
{
  "nss_disponible": false,
  "curp_disponible": true
}
```

El planner debe poder avanzar con CURP cuando el flujo lo permita.

---

# 5. Resolved Questions

Agregar a memoria:

```json
{
  "resolved_questions": []
}
```

Ejemplo:

```json
{
  "resolved_questions": [
    "tiene_imss",
    "tipo_trabajo",
    "nombre",
    "edad"
  ]
}
```

Una pregunta resuelta tiene prioridad sobre `preguntas_realizadas`.

Regla:

```text
Si question_key ∈ resolved_questions
→ Planner no puede seleccionarla nuevamente.
```

# 12. Criterios de aceptación

V3.1.2 no puede pasar a staging hasta cumplir:

- 100% tests semantic aprobados.
- Ninguna regresión del Intent Engine.
- Ninguna regresión de memoria existente.
- Sin cambios al comportamiento de Chatwoot hasta la fase de integración.
- Inspector puede explicar normalizaciones.
- Un conflicto solo puede solicitar aclaración una vez.
- Nombre conversacional rechazado.
- Slots alternativos funcionan.

---

# 13. Rollback

La primera fase del Semantic Engine será pasiva.

Mientras no esté integrada:

```text
rollback = eliminar src/semantic/
```

Durante integración:

1. Volver al release anterior.
2. Mantener `/app/data`.
3. Ignorar nuevos campos semánticos si existen.
4. No borrar memoria histórica.

Los nuevos campos deben ser opcionales para conservar compatibilidad.

---

# 14. Decisión arquitectónica

**Aprobación propuesta:** implementar el Semantic Engine primero de forma determinista.

No se utilizará OpenAI para equivalencias obvias como:

```text
No tengo trabajo = Estoy desempleado
```

El modelo solo podrá intervenir en una futura versión para expresiones ambiguas que las reglas no puedan normalizar con confianza suficiente.

Esto reduce:
- costo,
- latencia,
- variabilidad,
- falsos positivos.

Y aumenta:
- trazabilidad,
- consistencia,
- capacidad de prueba.
